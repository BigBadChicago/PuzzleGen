# Release process

How a change reaches a player, and what has to be true at each gate.

Four things ship on different cadences and must not be coupled: the platform,
a cartridge, the snapshot, and the client. The release process is mostly about
keeping them uncoupled.

## The four release trains

| what | cadence | gate |
|---|---|---|
| platform | when a change is ready | every suite green, including the platform's with no game installed |
| cartridge | per author | certification, which is regeneration plus review |
| snapshot | when content changes | coverage artifacts rebuild identically; days regenerate |
| client | app store cadence | manifest format compatibility, accessibility pass |

The coupling to avoid: a platform release that requires a client release, or a
snapshot rebuild that changes a published day. Neither is allowed, and both are
checked rather than trusted.

## Gates for a platform change

1. **Platform suite with no game installed.** This runs first, and it is the one
   that must not be merged into a single run with the game suites. A combined run
   would hide the property that the platform names no game, which is what makes
   the module boundary real.
2. **Every game suite with its game installed.**
3. **Both Python versions**, 3.11 and 3.13.
4. **Symbolic regeneration.** The symbolic snapshot and its committed day runs
   rebuild identically. This catches a change that alters output bytes.
5. **Version review.** If the change can alter the bytes of a published puzzle,
   `ENGINE_VERSION` moves. If it changes grading, `SCORING_VERSION` moves
   independently. A change that alters output and bumps nothing is the bug the
   version scheme exists to prevent.
6. **Invariant tests.** Layering, no game named in the platform, identity not
   derived from the deterministic generator, no token handling in the engine.

A platform change never regenerates a published day. New behaviour takes effect
from a future day key.

## Gates for a snapshot change

1. Coverage artifacts rebuild and the committed files are identical.
2. The new snapshot gets a new hash, and nothing republishes an old day against
   it.
3. Days generated against the new snapshot start from a future day key.
4. If a fact in the old snapshot was wrong and days depended on it, that is a
   retraction, which is an operations procedure and not part of this release.

## Gates for a client release

1. Reads every `PUZZLE_FORMAT_VERSION` currently published, and refuses the
   ones it cannot read with a message rather than a partial render.
2. Tolerates unknown fields within a format version it knows.
3. The rolling five day cache behaves: today, two past, two ahead; refresh after
   a play while connected, otherwise on next connection; a corrected day
   overwrites a cached day with no prompt.
4. Offline play grades on reconnection, and the server's grade is the grade.
5. Accessibility pass against the engine's rendered announcements, with a screen
   reader, on both platforms.

## Environments

| environment | holds | who sees it |
|---|---|---|
| development | a locally built snapshot, usually the symbolic one | the author |
| staging | a real snapshot and generated days, no players | the maintainer |
| production | published days and player data | players |

A cartridge under certification runs in staging against a named snapshot. The
thirty day run is a staging artifact that production regenerates.

## Rollback

Each train rolls back differently, and this is the part most likely to be
improvised badly in the moment:

- **Platform.** Redeploy the previous version. Days already published are
  untouched, because publication is immutable. Days generated by the bad version
  need review: if their bytes were wrong, they are a retraction, not a rollback.
- **Cartridge.** Deactivate it. If a published day of its was wrong, retract the
  day. Rolling a cartridge back to a previous version is a new certification,
  because the thirty day run is per version.
- **Snapshot.** Point generation back at the previous snapshot. Days already
  generated against the bad one are a retraction decision.
- **Client.** The app stores decide the pace, which is why the client must be
  able to refuse a day it cannot read: the platform cannot rely on a client
  rollback being fast.

The rule running through all four: rollback restores the ability to generate
correct days. It never changes a day that was published. A day that was wrong is
retracted.

## Who approves

One maintainer today, which means the process is a checklist rather than an
approval chain. The two gates that are not a judgement call and must never be
waived by the person who wrote the change:

- The platform suite passing with no game installed.
- Regeneration of committed day runs.

Both are machine checks. Waiving either is how the boundary and the determinism
promise are lost, and neither failure announces itself at the time.
